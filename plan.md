# Мини-CRM «Объекты и задачи»

## Краткое описание

Небольшая CRM для строительной компании. Постановщик заводит объекты (стройки) и ставит по ним задачи конкретным исполнителям. Исполнитель видит только свои задачи, берёт их в работу и отдаёт на проверку. Постановщик принимает задачу или возвращает на доработку с обязательным комментарием.

У задачи один линейный цикл статусов: **Новая → В работе → На проверке → Принята**, с веткой **На проверке → На доработке → В работе**. Каждая смена статуса пишется в историю: кто, когда, откуда, куда и комментарий, если он был.

Доступ закрыт в Postgres через RLS. Интерфейс только показывает разрешённые кнопки. Запрещённый переход, чужая задача и правка истории не проходят, даже если вызвать Supabase напрямую.

## План

Стек: Vite, React, TypeScript, React Router, Supabase (Auth + Postgres). Стили — свои, без тяжёлой UI-библиотеки: дизайн не оценивают, а код должен читаться на созвоне. Секрет `service_role` остаётся только в панели Supabase.

### 1. База и доступ

Один SQL-миграционный файл, чтобы репозиторий можно было поднять с нуля.

Таблицы:

| Таблица | Поля |
| --- | --- |
| `profiles` | `id` = `auth.users.id`, имя, роль `manager` или `executor` |
| `objects` | название, адрес, автор, дата создания |
| `tasks` | название, описание, объект, исполнитель, статус, автор, дата создания |
| `task_status_history` | задача, кто, когда, из какого статуса, в какой, комментарий |

Статусы в базе: `new`, `in_progress`, `review`, `accepted`, `rework`. Подписи на русском только в интерфейсе.

Роль читается функцией `current_user_role()` с `security definer`, чтобы политики не зацикливались на RLS таблицы `profiles`.

Правила чтения и записи:

- Постановщик видит и меняет все объекты и задачи, создаёт и удаляет их, назначает исполнителя.
- Исполнитель читает только задачи, где он исполнитель, и только те объекты, в которых такие задачи есть.
- Исполнитель не обновляет поля задачи. Смена статуса идёт отдельной функцией.
- Прямой `update` статуса запрещён триггером. Разрешён только внутри `transition_task`.
- При создании задачи статус всегда `new`, первую запись истории пишет триггер.
- `transition_task(task_id, to_status, comment)` проверяет текущий статус, роль и условие комментария. Разрешены только переходы из задания. Комментарий обязателен для перехода «На проверке → На доработке».
- На `task_status_history` нет политик insert, update и delete для клиента. Пишет только триггер и функция. Читать историю можно тем, кто видит саму задачу.
- Регистрация в Supabase Auth выключена. Пользователей создаём вручную в панели, строка в `profiles` появляется триггером на `auth.users`.

### 2. Интерфейс

Вход по email и паролю, без формы регистрации.

| Экран | Кто видит | Что делает |
| --- | --- | --- |
| Список объектов | постановщик — все, исполнитель — только свои | создание объекта только у постановщика |
| Карточка объекта | тот, кому объект доступен | задачи этого объекта и их статусы; постановщик создаёт, редактирует и удаляет задачи |
| Карточка задачи | автор постановки и назначенный исполнитель | поля, история и только те кнопки, которые разрешены этой роли в этом статусе |
| Мои задачи | исполнитель | его задачи по всем объектам |

Кнопки на карточке задачи:

| Статус | Исполнитель | Постановщик |
| --- | --- | --- |
| Новая | В работу | — |
| В работе | На проверку | — |
| На проверке | — | Принять; На доработку (с комментарием) |
| На доработке | В работу | — |
| Принята | — | — |

Ошибка от базы показывается текстом, если запрос всё же ушёл в обход кнопок.

### 3. Данные для сдачи

Три пользователя: один постановщик и два исполнителя. Два-три объекта и несколько задач в разных статусах, включая принятую и задачу на доработке с комментарием в истории. Пароли демо-пользователей — в README, не в коде фронтенда.

### 4. Сдача

1. Задеплоить фронтенд (Vercel) с `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`.
2. README: как поднять проект, как применить миграцию, какие демо-доступы.
3. Короткий текст для руководителя: как устроена работа с задачами, почему исполнитель не видит чужое даже через прямой запрос, почему историю нельзя переписать.
4. В том же тексте — решения, которые ТЗ не фиксирует, и что сознательно не вошло в срок.

### Порядок работ

1. Проект Supabase, миграция, политики, функция переходов, проверка прав из SQL Editor от имени разных пользователей.
2. Каркас Vite и экран входа.
3. Список объектов, карточка объекта, карточка задачи, «Мои задачи».
4. Демо-данные, деплой, README и текст сдачи.

Сначала база: её и будут проверять вопросами на созвоне. Экраны подключаются к уже закрытым таблицам и к одной функции смены статуса.

## Решения там, где ТЗ молчит

- Исполнитель не редактирует название, описание, объект и назначение. Он только двигает статус по разрешённым переходам.
- Постановщик тоже меняет статус только через `transition_task`, чтобы история не расходилась с фактом.
- «Принята» — конечный статус. Новых переходов из него нет.
- Исполнителем можно назначить только пользователя с ролью исполнителя.
- Удаление объекта постановщиком удаляет его задачи и их историю вместе с объектом. Отдельную строку истории через API удалить нельзя.
- Комментарий хранится только у перехода «На доработке». Остальные переходы пишутся без комментария.
- Интерфейс на русском.
