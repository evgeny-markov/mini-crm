# Мини-CRM «Объекты и задачи»

Небольшая CRM для строительной компании: постановщик ведёт объекты и ставит задачи, исполнитель видит только свои и двигает их по статусам. Доступ закрыт в Postgres, а не только кнопками.

## Запуск

Нужны Node.js `^20.19.0 || >=22.12.0` и проект Supabase.

```bash
npm install
cp .env.example .env
```

В `.env` укажите публичные ключи проекта (их можно светить во фронтенде):

```
VITE_SUPABASE_URL=https://<project>.supabase.co
VITE_SUPABASE_ANON_KEY=<anon key>
```

`service_role` в `.env`, в код и в репозиторий не кладётся.

Дальше в SQL Editor Supabase, по порядку:

1. `supabase/migrations/20261104120000_init.sql`
2. `supabase/seed.sql`

В Authentication выключите открытую регистрацию: Sign In / Providers → Email → выключить Allow new users to sign up.

```bash
npm run dev
npm run build
npm run lint:style
```

Фронтенд рассчитан на Vercel: в настройках проекта те же две переменные `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`. `vercel.json` отдаёт `index.html` на клиентские маршруты.

| Постановщик | manager@example.com | demo-manager |
| Исполнитель | ivan@example.com | demo-ivan |
| Исполнитель | olga@example.com | demo-olga |

Если `seed.sql` не сможет сам создать пользователей (схема `auth` на проекте отличается), создайте эти три учётки вручную в Authentication с теми же email и паролями, отметьте email подтверждённым и запустите `seed.sql` ещё раз. Скрипт найдёт их по email и проставит роли.

В базе три объекта и пять задач: новая, в работе, на проверке, на доработке с комментарием и принятая.

## Как устроена защита

Постановщик видит все стройки и все задачи. Исполнитель видит только задачи, где он указан исполнителем, и только те стройки, на которых такие задачи есть. Это правило записано в базе. Если открыть таблицу напрямую, чужие строки всё равно не придут.

Статус нельзя переписать обычным сохранением. Его меняет одна функция базы: она проверяет, кто спрашивает и из какого статуса в какой можно перейти. Вернуть задачу на доработку без комментария она отказывается. История пишется этой же функцией. Через интерфейс или прямой запрос историю нельзя дописать, изменить или стереть отдельной строкой. Если постановщик удаляет стройку или задачу, история уходит вместе с ней.

Регистрация с экрана входа выключена и в приложении, и в настройках Supabase. Секретный ключ администратора базы в приложение не попадает.

## Решения, где задание молчит

- Исполнитель не редактирует название, описание, объект и назначение. Он только переводит статус.
- Постановщик тоже меняет статус только через ту же функцию, чтобы история не расходилась с задачей.
- «Принята» — конечный статус.
- Исполнителем можно назначить только пользователя с ролью исполнителя.
- Комментарий хранится у перехода «На доработке». На остальных переходах он не записывается.
- Удаление объекта удаляет его задачи и историю.
- Роль берётся из профиля, который создаётся при появлении пользователя. В клиент роль не подставляется вручную.
- Интерфейс на русском. Коды статусов в базе английские.
